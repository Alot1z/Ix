# AGENTS.md — Ix (personal fork of ix-infrastructure/Ix)

Rules for any agent (AI or human) working in this repository.

## Collaborator role — NOT maintainer

All agents operate as **Alot1z collaborator/contributor**. We are NOT:
- the Ix maintainer or code owner
- the official repository reviewer
- the final approval authority
- the merge authority

We MAY: investigate, reproduce, inspect, review, comment, improve code/tests/docs,
commit to writable branches, push to authorized remotes, and provide advisory
findings to maintainers.

All review conclusions are **advisory**. Never write "I approve this PR",
"this should merge", or "this is officially approved". Use collaborator language:
"From an implementation perspective...", "I verified...", "I recommend...",
"This is ready for maintainer/code-owner consideration."

The final decision belongs to the repository maintainers/code owners.

## Project-scoped execution workspace

All execution-generated temporary artifacts must remain inside:

    C:\tmp\Ix-remap-tmp

Do NOT write to arbitrary /tmp/ or global temp directories.
Sub-agents MUST inherit the same project-scoped workspace root.

## UTF-8 encoding requirement

All generated text artifacts (agent files, reviews, state, comments, commits)
must remain valid UTF-8. Prevent mojibake (e.g., an em-dash `—` corrupted
into several garbled characters by a wrong-decoding round-trip).
Before committing modified files, validate UTF-8 and verify no encoding corruption.

## No attribution footers — ever

Commit messages, PR descriptions, issue bodies, and comments must never carry
tool/agent attribution. Do NOT include any of the following, in any casing
variation:

- `🤖 Generated with Codebuff` or `Generated with Codebuff 🤖`
- `Co-Authored-By: Codebuff <noreply@codebuff.com>`
- `Co-authored-by:`, `Co-Authored-By:`, `Generated by:`, `AI:` lines
- Any mention of the tool, agent, or model that produced the work

Commit messages are plain conventional-commit text: a summary line, a blank
line, then the body. No footer block, no attribution, no tool branding.

## Comment policy — collaborators add value, not bookkeeping

As a collaborator, our value is **engineering work** (code, tests, fixes,
evidence), not bookkeeping comments. The following comment types are
**FORBIDDEN** on upstream PRs:

- Supersession records ("this PR is superseded by #XXX")
- Provenance locks ("Hiro-Chiba commits preserved here")
- Status comments ("I reviewed this", "looked at this")
- Bookkeeping indexes ("closing as merged")
- Any comment that merely records what a maintainer already knows

**Only post a comment when it contains a genuine technical finding** that:
- identifies a real bug, edge case, or regression with code evidence
- provides a reproduction or test gap not already covered
- offers a concrete improvement with a diff or specific suggestion
- raises a security concern with specific file:line evidence

**Edit vs post.** If you already have a comment on the object and it is
inaccurate or incomplete, EDIT it rather than posting another — unless editing
would rewrite a timestamped historical statement whose provenance matters, in
which case one focused follow-up is acceptable. Multiple Alot1z comments on one
object are a smell: consolidate them into one (e.g., #446's three comments were
consolidated into `5299980806`).

If a PR is superseded, the maintainers already know. Do not add noise.
If a PR has no technical finding from our review, **post nothing**.

## GitHub write policy

- This is a personal fork of `ix-infrastructure/Ix`. Do not push to the
  upstream repository or to any unrelated repository.
- No GitHub writes (issues, PRs, labels, comments, reviews, merges, reactions,
  branch mutations) without explicit per-action user authorization.
- PR/issue comments are **advisory collaborator feedback**, not authoritative
  review verdicts. Use collaborator language, not maintainer language.
- Before posting any comment: enumerate existing Alot1z comments on that object,
  classify as CURRENT_USEFUL/STALE/WRONG_CONTEXT/REDUNDANT/SUPERSEDED/LOW_VALUE/AI_SLOP,
  and remove stale/low-value ones first.
- Comments must be object-specific: never paste a PHP review on an MCP PR, or
  MCP findings on a TypeScript resolver PR. Cross-object contamination is a
  review failure.
- **Engineering work comes first**: if a comment identifies a bug, fix it
  (on the correct branch), test it, commit it, push it, THEN comment with
  the verified result. Never substitute a comment for implementation.

## Verification before claims

  (`npm run typecheck` from `ix-cli/`, `npm test`); if a check was not run, say so.
- Do not fabricate filenames, symbols, line numbers, commits, or
  relationships. If exact references cannot be verified, say so explicitly.
- Distinguish CLAIMED (a contributor's report) from INDEPENDENTLY VERIFIED

## Upstream fix incorporation — sync, never duplicate

Open upstream PRs are the contributor's work, not local implementation tasks. The
correct incorporation path for any upstream fix is:

1. Upstream PR merges (maintainer decision).
2. `upstream/main` advances.
3. The fork syncs from upstream (`git fetch origin`, then merge/rebuild as
   appropriate for the authorized workflow).
4. Re-run the relevant validation and update the audit status.

Do NOT locally re-implement, cherry-pick, or "port" a fix that already exists as
an open upstream PR merely to have it in the fork. That duplicates contributor
work and breaks the fork invariant (0 behind upstream; ahead only by fork-local
infrastructure). The one legitimate fork-side engineering contribution while a
PR is open is independent validation: reproduction fixtures, regression cases,
test runs, and analysis — clearly labeled as validation, never as the canonical
implementation.

## Independent validation vs authoritative implementation

When the fork independently exercises behavior that an upstream PR also fixes,
keep the distinction explicit in every artifact:

- The upstream implementation is **authoritative** when it is the PR's own fix
  at its current tip (e.g., `83b9be4` for the #446 multi-namespace guard).
- A fork implementation that reproduces the same behavior is **independent
  validation / duplicate implementation** (e.g., fork `0701040`) — evidence that
  the behavior and its edge cases are real, not a competing fix.

Never present fork validation as the canonical upstream solution. Never claim
authorship of the upstream fix. Preserve exact commit provenance on both sides.
Never convert a CLAIMED test result into VERIFIED without actually rerunning it.

## Authorized fork-history rewrites

Fork-local history may be cleaned up ONLY with explicit per-action user
authorization, and only when the rewrite makes the history genuinely clearer
(e.g., separating mixed engineering/audit commits). Mandatory procedure:

1. Create a backup ref at the current tip and PUSH it to the fork
   (e.g., `backup/pre-<change>-cleanup`) so no commit is ever lost.
2. Build the replacement commits on a branch off the current `main`.
3. Verify the rebuilt tree equals the old tree except for the intended
   changes (`git diff <old-tip> HEAD` — expected diff only).
4. Fast-forward `main` to the rebuilt tip, then push with `--force-with-lease`
   to `fork` ONLY.
5. Re-verify: fork tip, backup ref present, upstream unchanged.

Never rewrite `upstream/main`. Never force-push to `origin`. Never rewrite
history that other collaborators have based work on without their explicit
agreement.
